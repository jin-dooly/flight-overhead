## 2. 서버 작업

### 2-1. 폴러 일반화 (`dc55023`)

기획서: "격자 폴러의 구독 수 추적, 예비 전환, 백오프, retained 발행을 그대로 씀".

- 기존 `GridPoller`는 격자 전용이었습니다(토픽 파싱, 좌표 반경 조회가 안에 박혀 있음). 이걸 **`TopicPoller<K, P>`**로 일반화했습니다.
  - `K`는 토픽에서 꺼낸 조회 키(격자는 `{lat, lon}`, 따라가기는 `hex`)
  - `P`는 발행할 값(격자는 `Snapshot`, 따라가기는 `FollowSnapshot`)
  - 폴러에 넘기는 것: `parseTopic`(토픽 → 키), `fetch`(키 → 결과), `publish`
  - 구독 수 추적, 즉시 1회 조회 후 간격대로, 백오프, "조회 중에 마지막 구독자가 떠나면 발행 안 함"은 전부 그대로
- **`RequestSpacer`:** 요청 시작 간격 250ms 예약표를 클래스로 뺐습니다. 격자 폴러와 따라가기 폴러가 같은 adsb.lol을 부르므로 **예약표 하나를 같이 써야** 요청이 몰리지 않습니다(`app.ts`에서 하나 만들어 둘에 넘김).
- `GridPoller`는 같은 API로 `TopicPoller`를 감싸기만 해서, 기존 테스트 40개가 수정 없이 통과했습니다. 리팩터링의 안전망이 테스트였습니다.

### 2-2. 따라가기 토픽과 타입 (`dc2c4c1`)

- `followTopic(hex)` → `aircraft/71c9a3`, `parseFollowTopic(topic)` → `71c9a3` | null
  - 소문자 16진수 6자리만 허용. 와일드카드(`+`, `#`), 대문자, `~`로 시작하는 TIS-B 임시 ID는 거절
  - 격자 토픽과 같은 이유로 엄격하게 합니다. 같은 기체에 토픽이 여러 개 생기지 않게, 그리고 브로커 권한 검사가 이 함수 하나로 끝나게
- `FollowedAircraft = Aircraft & { onGround: boolean }`, `FollowSnapshot = { hex, aircraft: FollowedAircraft | null, source, fetchedAt }`
  - 기획서 데이터 모델의 `Aircraft`는 바꾸지 않고 따라가기 전용 타입을 따로 만들었습니다.
  - `aircraft: null`은 "응답은 왔는데 그 기체가 없음"(수신 범위 밖)입니다. 조회 실패와 구분하려고 둡니다.

### 2-3. 따라가기 폴러 (`a1b72af`)

**조회 (`sources/`)**

- 각 소스 어댑터에 `fetchByHex(hex)`를 추가: adsb.lol `/v2/hex/{hex}`, adsb.fi `/api/v2/hex/{hex}`
- 정규화 `normalizeFollowed`: 격자와 같은 규칙인데 **지상 기체를 버리지 않고** `onGround: true`로 표시합니다(기획서: 지상 여부를 함께 보내서 "착륙했어요"). 고도가 `"ground"` 문자열이라 그 필드만 빼고 공통 정규화를 씁니다.
- `normalizeHexResponse`: 응답 목록에서 그 hex를 찾음. **목록 키를 `ac`와 `aircraft` 둘 다 봅니다.** adsb.fi는 좌표 조회는 `aircraft`, 기체 ID 조회는 `ac`를 씁니다(아래 6번에서 1회 확인).
- 예비 전환 `createFallbackHexFetcher`: 격자와 같은 규칙(메인 실패 시 예비, 둘 다 실패면 degraded). 기체가 없으면 실패가 아니라 `aircraft: null`로 발행합니다.

**연결 (`realtime.ts`의 `connectFollowPollerToBroker`)**

- 격자 폴러와 같은 `subscribe` / `unsubscribe` / `clientDisconnect` 이벤트를 받습니다. 각 폴러는 자기 토픽이 아니면 무시합니다.
- 소스 상태(`status/source`)는 알리지 않습니다. 그 토픽은 "격자 조회 결과"라서, 따라가기 결과를 섞으면 화면의 "데이터 지연"이 엉뚱하게 깜빡일 수 있습니다.

**남용 방지 (기획서: 연결 하나당 따라가기 1개, 서버 전체 동시 따라가기 수 제한)**

- **연결당 1개:** `TopicPoller`의 `maxTopicsPerClient: 1`. 한 연결이 다른 기체를 구독하면 이전 기체는 **폴링 대상에서 뺍니다**.
  - 브로커 구독 자체를 거절하지 않는 이유: 화면에서 기체를 바꿀 때 "이전 해제"와 "새 구독"이 거의 동시에 가는데, 거절 방식이면 순서에 따라 새 구독이 실패할 수 있습니다. 폴링에서 빼는 방식은 순서와 상관없이 비용이 늘지 않습니다.
- **서버 전체 상한:** `MAX_FOLLOWS`(기본 20). `createBroker({ allowSubscribe })`에 검사 함수를 넘겨서, 상한이 차면 **새 기체** 구독만 SUBACK 128로 거절합니다. 이미 누가 따라가는 기체는 추가 조회가 없으므로 허용합니다.
- `/health`에 `activeFollows` 추가

## 3. 프론트 작업

### 3-1. 상태와 순수 함수 (`ab79b58`)

- **`lib/follow.ts` `deriveFollowPhase`:** waiting(첫 위치 기다림) / active / lost(30초 넘게 위치 없음) / landed(끝 상태)
  - 끊김 기준 30초는 보간 예측을 멈추는 시간(`MAX_PREDICT_MS`)과 같게 했습니다. 그래서 "신호가 끊겼어요"가 뜨는 순간 마커도 멈추고 흐려집니다.
- **`lib/geo/bearing.ts` `bearingDeg`:** A에서 B를 바라보는 방위각. "내 위치 ↖ 107 km" 화살표에 쓰고, 하늘 모드에서 비행기 좌우 배치에도 씁니다.
- **`store/follow.ts`:**
  - `startFollow(aircraft)`: 지도에서 보던 값을 첫 위치로 씁니다. 서버 첫 응답(몇 초)을 기다리는 동안 비행기가 사라지지 않게
  - `applyFollowSnapshot`: 마지막 위치, 지나온 경로, 함께 이동한 거리, 착륙 시각 갱신
    - 같은 위치 재전송(retained)과 다른 기체 메시지는 무시
    - 기체가 응답에 없으면(`null`) 마지막 위치를 유지
    - 한 번에 100km 넘게 튀면 이동 거리에 더하지 않고 경로를 새로 시작(아래 4번 참고)
    - 착륙이 확인되면 그 뒤 메시지는 무시(끝 상태)
- **`hooks/useFollowSubscription.ts`:** 따라가는 동안 `aircraft/{hex}` 구독. **끝내거나 착륙하면 바로 해제**해서 서버 조회를 멈춥니다. 거절(SUBACK 128)되면 `rejected` 표시

## 4. 내린 결정 (작은 결정)

- 서버 전체 동시 따라가기 상한 기본 20 (`MAX_FOLLOWS`). Render 무료 플랜 한 대와 adsb.lol 호출량을 생각한 값. 격자 폴링과 요청 간격 예약표를 공유함.
- 따라가기 폴링 간격과 백오프는 격자와 같음(5초, 최대 60초).
- 연결당 1개는 "거절" 대신 "이전 기체를 폴링에서 뺌"으로 구현(2-3 이유).
- 따라가기 결과는 `status/source`에 반영하지 않음.
- `aircraft/{hex}`는 소문자 6자리만. TIS-B 임시 ID(`~…`)는 따라가기 버튼을 숨김.
- 착륙 후 서버 구독을 해제함(조회 비용 절약). 착륙 카드에서 보여 주는 위치는 마지막으로 받은 값.
- "계속 기다리기"를 누르면 끊김 카드 대신 평소 카드를 보여 줌("N초 전 기준"이 주황색).
- 지나온 경로 점은 50m 이상 움직였을 때만 더함(제자리 떨림 방지). 한 번에 100km 넘게 튀면 이어진 경로로 보지 않음.
- 따라가는 동안 다른 비행기는 그리지 않음(격자 데이터는 내 위치 근처뿐이라, 비행기가 멀어지면 어차피 없음).
- 새 화면 파일은 `components/follow/`, 지도 동작은 `components/map/FollowMapMode.tsx`.

## 5. 직접 확인한 것

로컬 서버(`tsx watch`라 브랜치를 바꾸면 자동으로 새 코드로 재시작)와 폰 크기 브라우저로:

1. 카드의 "따라가기"를 누르면 `/health`가 `activeFollows: 1` → 서버가 기체 ID 조회를 시작함
2. 지도 끌기가 꺼지고, 확대/축소 버튼이 보이고, 비행기가 카드 위 보이는 영역 가운데에 고정됨
3. 그 기체(BOX580, 인천공항 지상 근처)는 30초 넘게 위치가 안 와서 "신호가 끊겼어요" 카드가 뜸
4. "내 위치로 돌아가기"를 누르면 `activeFollows: 0`, 화면이 평소 지도로 돌아옴
5. 진행/착륙 카드는 스토어에 값을 직접 넣어서 목업과 같은지 확인. 이때 가짜로 넣은 기체 ID `abc123`이 **실제로 미국 애리조나 상공의 기체**였고, 서버가 그 위치를 보내 와서 "함께 이동"이 1만 km가 됐습니다. 이걸 보고 "한 번에 100km 넘게 튀면 이동 거리에 더하지 않음"을 추가했습니다.

## 6. 확인 필요

1. **adsb.lol `/v2/hex/{hex}` 응답 형식을 직접 확인하지 못했습니다.** 1회 호출했을 때 `429 rate limit exceeded`가 왔고, 규칙대로 다시 부르지 않았습니다. 기획서와 readsb 형식대로 `ac` 목록으로 처리했고, 형식이 달라도 `ac`/`aircraft`를 둘 다 보며, 실패하면 adsb.fi로 넘어갑니다. adsb.fi `/api/v2/hex/{hex}`는 1회 확인: 목록 키 `ac`, 필드는 좌표 조회와 같음.
2. **adsb.lol 429.** 그 시각에 제 미리보기 탭이 로컬 서버를 통해 인천 격자를 5초마다 폴링하고 있었습니다. 같은 IP에서 격자 폴링과 다른 요청이 겹치면 제한에 걸릴 수 있다는 뜻입니다. 배포 서버(Render)는 IP가 다르지만, 사용자가 많아져 격자와 따라가기가 늘면 같은 일이 생길 수 있습니다. 지금은 예비 소스 전환으로 버팁니다. 폴링 간격 5초가 안정적인지는 기획서 열린 질문에도 있습니다.
3. **실제 비행 중인 기체를 끝까지(착륙까지) 따라가 보지는 못했습니다.** 새벽이라 비행기가 적었고, 실제 API 호출을 오래 하지 않으려고 짧게 확인했습니다. 낮에 한 번 착륙까지 따라가 보시길 권합니다.
4. **출발·도착 공항 표시(adsb.lol `/api/0/routeset`)**는 기획서에서 "정확도 확인 전까지 표시하지 않음"이라 만들지 않았습니다.
5. **main에 합칠지.** 따라가기는 `development`에만 있습니다. 배포하려면 `development`를 main에 합치면 되고, 서버(Render)와 프론트(Vercel)가 같이 배포돼야 합니다. 프론트만 먼저 나가면 서버가 `aircraft/…` 구독을 거절해서 "따라가기를 시작할 수 없어요"가 뜹니다.

## 7. 직접 확인하는 방법

```bash
git checkout development
pnpm install
pnpm test
pnpm --filter @flight/server dev
pnpm --filter @flight/web dev
```

브라우저에서 비행기를 고르고 "따라가기"를 누른 뒤, 다른 터미널에서 서버 조회가 시작됐는지 봅니다.

```bash
curl http://localhost:4000/health
```

`"activeFollows":1`이 보이면 서버가 그 기체를 조회하는 중입니다. 끝내기를 누르면 0으로 돌아갑니다. 실제 API를 부르므로 오래 켜 두지 마세요.
